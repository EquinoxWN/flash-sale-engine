## Burst demo (`make demo`)

20,000 HTTP buyers (256 in flight on the client) for 1,000 units, gateway rate 5,000/s with a burst
of 1,000, 64 in-flight Valkey slots, token cap 2,000, each buyer retries a shed answer up to 3
times. Backend: jedis-mock.

```
backend: jedis-mock (in-process Redis-protocol server running Lua on LuaJ), not Valkey
burst: sale=demo units=1000 buyers=20000 concurrency=256 rate=5000/s burst=1000 token_cap=2000 in_flight=64
requests: 35605 in 25.99 s (1370 req/s), latency p50 130.0 ms, p99 687.9 ms
shed: rate_limited=0 busy=14086 queue_full=11189 gave_up=478 errors=3
buyers: 20000, tokens issued: 2000, won: 1000, sold_out answers: 7330
audit: units=1000 sold=1000 in_orders=1000 remaining=0 winners=1000 oversold=0 -> OK
```

### What the numbers show (Analyze)

- **Zero oversold, full sell-through:** 1,000 units, 1,000 winners, stock 0, orders and counter agree.
- **Shedding worked in front of the store:** only 2,000 buyers ever got a token (the cap), 11,189
  token requests were refused as `queue_full` and 14,086 requests were shed as `busy` before
  reaching the store. The rate limit (5,000/s) never triggered because jedis-mock itself limited
  throughput to about 1,370 requests per second; the in-flight cap was the active shedding step.
- **The bottleneck is the local backend, not the design:** jedis-mock runs every script through
  LuaJ inside a Java server on a busy laptop. These latency and throughput figures are not
  Valkey figures and must not be quoted as such.
- **3 answers were counted as client-side errors** (an HTTP I/O failure or an unexpected status;
  the M1 burst client counts them but does not record which). They do not affect correctness: the
  audit is computed from the store's state, not from client answers.

Defect found and fixed: `OversellTest.twoThousandBuyersForOneHundredUnitsLeaveExactlyOneHundredWinners`
failed locally with `JedisException: Could not get a resource from the pool` after about 30 s. It
failed the same way with the old versions above, so the upgrade did not cause it. A thread dump taken
during the run showed the root cause: 256 virtual threads (the carrier-pool limit) waiting in
commons-pool2 2.13.1 `GenericObjectPool.create()` (`Object.wait` inside `synchronized`, which pins
the carrier thread on JDK 21), while the threads that held the 66 connections could not get a
carrier to read their replies; every pool wait then ran into the 30 s timeout. The gateway never
hits this, because it lets at most `maxInFlight` requests reach the pool. Fix: the test opens all
pooled connections (`getPool().addObjects(maxTotal)`) before the 2,000-buyer race, so no borrower
waits in `create()`. `OversellTest` then took 4.3 s.

## Quality check 2026-11-01

The 10 engineering rules were checked against the code; the table, the evidence and the mutation
table are in [docs/quality/2026-11-01.md](../quality/2026-11-01.md).

- Fixed: the burst client retried every 503, including `store_unavailable`, which the gateway also
  returns when Valkey times out after `buy.lua` may already have run. With a per-user limit above 1,
  such a retry could buy a second unit. It now retries only shed answers (`rate_limited`, `busy`);
  `BurstTest.onlyShedAnswersAreRetriedNotAStoreFailureWhoseOutcomeIsUnknown`.
- Mutation check (17 hand mutations of the Lua scripts, rate limiter, gateway, audit, burst client
  and ids): 14 killed before; one is equivalent. The two real survivors now have tests: a blind
  read-then-write in the rate limiter (only caught by chance before; a 200-round platform-thread
