# Quality check 2026-11-01

The ten quality rules checked against the code, with evidence. Java 21 (Temurin 21.0.12), Maven
3.9.11, Windows 11, Intel Core i7-13700H. Locally the backend is jedis-mock; CI also runs the
parameterized tests against a real Valkey 9.0 container.

| # | Rule | Status | Evidence |
|---|---|---|---|
| 1 | Every call can fail | pass | Every Valkey call goes through a pooled client with connect, read and pool-wait timeouts (`Main.connect`, default 2 s, `--timeout-ms` 100 to 60,000). A lost connection becomes 503 `store_unavailable`, any other runtime failure 500 (`Gateway.handle`); the CLI turns `JedisException` and `IOException` into exit 2 (`Main.run`). The burst client has a 5 s connect and 10 s request timeout, bounded attempts (1 to 100) and a growing random back-off (`Burst.callWithRetry`). `LuaScript.run` falls back from EVALSHA to EVAL only on NOSCRIPT. The one empty `catch` (`Backends.mockUri` shutdown hook, test code) is commented: the JVM is exiting. |
| 2 | Writes safe to retry | fixed | `load.lua` refuses to overwrite a loaded sale unless forced; `admit.lua` returns the same token to a user who asks again; `buy.lua` checks token, per-user limit and stock in one atomic script. Found: the burst client retried every 503, including `store_unavailable`, which can come after `buy.lua` ran (socket timeout on the reply), so with a per-user limit above 1 a retry could take a second unit. It now retries only answers that prove the purchase did not run (`rate_limited`, `busy`); test `onlyShedAnswersAreRetriedNotAStoreFailureWhoseOutcomeIsUnknown`. Remaining: a client that retries `POST /buy` itself after a timeout is not deduplicated beyond the per-user limit (known limitation; idempotent orders are M2 step 4). |
| 3 | No race conditions | fixed | Stock is only changed inside Lua scripts, which Valkey runs one at a time (2,000-buyer race and 25 randomized sales in `OversellTest`; the negative control shows a Java read-then-write oversells). The rate limiter is one `AtomicLong` updated by compare-and-set; counters are atomics; the in-flight cap is a `Semaphore`. Found (test gap): replacing the CAS with a blind write survived the 64-virtual-thread test, which catches it only by chance; `platformThreadsRacingOnOneSlotNeverOverAdmit` (200 rounds, 16 OS threads, frozen clock) kills it on every run. |
| 4 | Don't trust the clock | pass | The rate limiter and all latencies use `System.nanoTime()` (`RateLimiter`, `Burst.post`, `Burst.run`); no `currentTimeMillis` deltas. Key expiry is Valkey's TTL; no timestamps are stored. |
| 5 | Read before changing | pass | Jedis 8.0.2 APIs (`RedisClient`, `DefaultJedisClientConfig`, `evalsha`/`eval`) compile with `-Xlint:all -Werror`. Environment: `VALKEY_URL` (documented in the README, overridden by `--valkey`) and `GITHUB_ACTIONS` (only switches the CI annotation). Every README path exists. |
| 6 | Never break compatibility | pass | HTTP answers and JSON bodies unchanged; the Lua scripts keep their result codes (`LuaScriptsTest`). Key names are fixed per sale with one hash tag (`SaleKeys`). |
| 7 | One source of truth | pass | Valkey holds the only copy of stock, tokens and orders; the gateway caches nothing. Scripts are cached by Valkey under their SHA-1 and re-sent on NOSCRIPT (`scriptsAreResentWhenTheServerForgetsThem`). Versions: Java 21 in `pom.xml`, README and CI agree. |
| 8 | Small changes, no secrets, validate input | pass | Secret scan (`grep -rniE "password\|secret\|api_?key\|token"`): only the queue-token feature and the Valkey URL password parsing (no literal secrets); test tokens are obviously fake. Every input is validated: sale, user and token ids by pattern (`Ids`), quantity 1 to 100, no request bodies, path and query length caps (`Gateway`), every CLI option by range (`Main`), `SaleConfig` bounds. No new dependency (the new test uses the JDK `HttpServer`). |
| 9 | Tests that can fail | fixed | No tautologies, skips or `@Disabled` (`grep -rn "@Disabled\|assumeTrue\|assertTrue(true)"`: none). Mutation table below: 14 of 17 killed before, one equivalent, both real survivors killed after. |
| 10 | Re-verify | pass | `bash .tmp/check.sh`: spotless clean, `-Xlint:all -Werror` clean, `Tests run: 75, Failures: 0, Errors: 0, Skipped: 0`, OSV `19 dependencies checked, 0 with known vulnerabilities`, `flash-sale-engine: OK`, `CHECK PASS`. The real-Valkey cases run in CI. |

## Known limitations

- `POST /buy` has no idempotency key: a client that resends a purchase after a timeout may take a
  second unit when the per-user limit is above 1 (never more than the limit, never oversold).
  Idempotent order creation is M2 step 4 of the roadmap.
- Valkey throughput is not measured (jedis-mock numbers only, as the README says).
